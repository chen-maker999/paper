\section{Experimental Setup}
\label{sec:setup}

\paragraph{Trajectories.} We use public trajectories submitted to the SWE-bench
leaderboards~\citep{jimenez2024swebench} (\cref{tab:corpus}). \emph{In-domain}:
SWE-agent~\citep{yang2024sweagent} on SWE-bench Lite with five LLMs---GPT-4,
Claude~3 Opus and GPT-4o (SWE-agent 0.x interface), Claude~3.7 Sonnet and
Claude~4 Sonnet (1.x interface)---1{,}479 trajectories. \emph{Cross-scaffold}:
SWE-bench Verified runs of OpenHands~\citep{wang2025openhands} with Claude~4
Sonnet, GPT-5, Kimi~K2, Qwen3-Coder-480B and Devstral-Small, and of SWE-agent
with SWE-agent-LM-32B and Kimi~K2---3{,}500 trajectories, including three
open-weight models and two log formats (native and prompt-based function
calls). A further OpenHands export (Claude Opus~4.5) records every tool call as
``\texttt{Action: unknown}'' and is excluded because no actions can be
recovered. All token counts use a real BPE tokenizer (the legacy Claude
tokenizer distributed with the MIT-licensed \texttt{anthropic} SDK).

\paragraph{Splits and protocol.} The first ten instances (alphabetically) of
every Lite model form a \emph{development} set used for all design and
hyper-parameter decisions; results are reported on the remaining 1{,}429 Lite
trajectories. For the cross-scaffold set we sample 150 trajectories per
configuration (1{,}050) and drop instances that also occur in SWE-bench Lite.
SKC's utility model is trained with leave-one-LLM-out, instance-disjoint folds
on Lite (\cref{sec:method}); on the cross-scaffold set it is a single model
trained on all Lite trajectories, so neither the scaffold, the LLM nor the task
was seen in training. For each trajectory and budget
$B\in\{4\text{k},8\text{k},16\text{k},32\text{k}\}$ we evaluate up to six
decision points whose history exceeds $B$, compressing the history with every
method and probing state (all keys written so far), use and copy
(\cref{sec:formulation}). We report per-trajectory macro averages with 95\%
bootstrap confidence intervals and paired bootstrap tests over trajectories.

\paragraph{Baselines.} Seven model-free compressors covering the families used
in practice (settings in \cref{app:settings}): \textbf{recency window} (FIFO
truncation, task pinned); \textbf{observation masking}, which keeps all agent
turns and masks all but the last ten tool outputs~\citep{lindenbauer2025complexity};
\textbf{truncate observations}, which caps older tool outputs; \textbf{BM25} over
whole turns and over the same 12-line \textbf{chunks} SKC uses (salience-based
selection~\citep{robertson2009bm25}); \textbf{self-information} line pruning, a
model-free variant of Selective Context~\citep{li2023selective}; and
\textbf{random} selection. \textbf{SKC-basic} is the heuristic variant of SKC
without layers 2--3. LLM summarization is evaluated in the LLM-in-the-loop study.

\paragraph{LLM-in-the-loop study.} To check that what the ideal reader finds is
also usable by a model, we sample 60 decision points per Lite LLM (300 in total,
8k budget) and give the compressed context to three reader LLMs from two
families (Qwen3.8-Flash, Qwen3.7-Flash, DeepSeek-V4-Flash; thinking disabled,
temperature 0). Task~A (\emph{state QA}, 217 points) asks for the last line of
the most recent output of a command last run at least three steps earlier;
answers are graded correct, stale (an earlier run's output), unknown or wrong.
Task~B (\emph{next action}) asks for the agent's next tool call; we report
whether it names the same file as the true action and identifier-level F1. An
\textbf{LLM summary} baseline replaces the history before the last two turns by
a summary of at most 4k tokens written by the same reader model.

\section{Results}
\label{sec:results}

\subsection{What long agent contexts are made of}
\label{sec:corpus}

\Cref{tab:corpus} and \cref{fig:corpus} characterize the 4{,}979 trajectories.
Tool outputs make up 65--89\% of all tokens. Between 23\% and 55\% of tokens are
lines that occur again later in the same history (repeated file views, re-run
tests, re-typed code), redundancy that is invisible to per-turn compressors but
removed by content compaction (\cref{prop:dedup}). Recent LLMs run longer and
reach further back: for OpenHands with Qwen3-Coder or Claude~4 Sonnet the median
trajectory has 64--66 steps and 41--42k tokens, and 80--81\% of the identifiers
their actions use first appeared more than ten steps earlier (21\% for Claude~3
Opus). A median trajectory rewrites 3--7 state keys at least once. Long
horizons therefore combine long-range dependencies, heavy repetition and
frequent overwrites---the three conditions our analysis identifies as hard for
windows (forgetting by age), for per-turn selection (staleness) and for budget
efficiency (redundancy).

\paragraph{State retention.} \Cref{tab:main} and \cref{fig:real-budget} give the
main comparison. In-domain, SKC keeps the current value of 65.0\% / 74.8\% /
85.0\% / 91.8\% of all state variables at 4k / 8k / 16k / 32k tokens, against
57.8\% / 67.3\% / 75.7\% / 82.5\% for the best baseline (random selection) and
45--72\% for the recency window. The paired differences, $+7.2$, $+7.5$, $+9.2$
and $+9.4$ points, have 95\% intervals of width below 1.6 points ($p<10^{-3}$).
SKC-basic, which spends its budget on the ledger first, keeps even more state at
small budgets (69.7\% at 4k). The gain transfers to unseen scaffolds and LLMs:
on the cross-scaffold set SKC improves on the best baseline by $+4.9$, $+5.9$,
$+4.1$ and $+3.4$ points (all $p<10^{-3}$), and SKC-basic by up to $+13.4$, for
each of the seven configurations (\cref{app:results}). Budgets correspond to
real compression: at 4k, SKC reduces the average history of 18.6k tokens by
$4.7\times$ (at 32k, $1.7\times$) in 0.1--0.25\,s per step on one CPU core
(\cref{tab:efficiency}).

\paragraph{Staleness.} Selection methods leave stale state on 1.0--2.8\% of all
probes in-domain. This average hides the dependence on overwrites predicted by
\cref{prop:stale} (\cref{fig:stale-real}): for keys written three or more
times, BM25 and random selection are stale on 9--13\% of probes, i.e.\ 13--18\%
of the values they retain for such keys are outdated. SKC is stale on
0.1--0.3\% of probes, statistically indistinguishable from the recency window
(the least stale baseline; $p\ge0.18$ at every budget in-domain) while keeping
19--21 points more state.

Windows and masking are as good as SKC for keys written in the last five steps
and collapse beyond ten, as \cref{prop:window} predicts; SKC degrades
gracefully and still keeps most keys written 20--40 steps earlier.

\paragraph{Information the agent uses next.} The key-free probes paint a more
nuanced picture. SKC preserves long-range identifiers as well as the best
baseline in-domain (79.5\% vs.\ 80.5\% for chunk-level BM25 at 4k; differences of
1--1.6 points, $p\ge0.05$) and better than every other baseline (window 54.5\%,
masking 55.0\%, random 74.0\%). For lines the agent later \emph{copies},
chunk-level BM25 is best (75.7\% vs.\ 67.6\% at 4k; the gap shrinks to 2.7
points at 32k); on the cross-scaffold set the gap to BM25 is 1.5--4.7 points on
use and 0.7--4.7 on copy. Copying is dominated by an agent re-typing parts of a
script or edit it wrote a few steps before, which lexical overlap with the
latest agent turn captures directly. \Cref{fig:frontier} shows that this is a
trade-off governed by $\lambda$ rather than a ceiling: with $\lambda=0$, SKC
matches BM25 on use at 4k while keeping 5 points more state, and every
operating point with $\lambda\ge0.1$ keeps more state than every baseline. The oracle utility in
\cref{sec:ablation} shows that better utility prediction alone would raise use
and copy to 93--95\%.

\Cref{tab:llm} and \cref{fig:llm} show that the ideal-reader gains are usable by
real models. With SKC's context, readers answer 77.0\% / 50.2\% / 59.9\% of the
state questions correctly, against 40.1\% / 24.9\% / 27.2\% with the best
baseline; the improvements ($+25$ to $+37$ points over the window, $+29$ to $+45$
over masking and BM25) are significant for all three readers ($p<10^{-3}$) and
come mainly from turning ``unknown'' answers into correct ones. LLM summaries,
although written by the same model, answer only 2--7\% of the questions: they
describe what was done (``ran the reproduction script, which still failed'')
rather than preserving the exact state, the paraphrase drift that verbatim
ledger values avoid. Part of this gap is budget: the summaries use only 0.5--0.9k
tokens. The budget-matched variant that fills the remaining budget with the most
recent turns (\emph{Summ.+recent}, $\approx$7.5k tokens, the design of production
agents) recovers 18--38\%---but still trails the plain recency window by 2--7
points and SKC by 32--39 points ($p<10^{-3}$ for all readers): spending part of
the budget on a summary loses more exact state than it preserves. For
next-action prediction, SKC is statistically indistinguishable from window,
masking, BM25 and Summ.+recent in 23 of 24 comparisons (exceptions: 5.3 F1
points below masking for Qwen3.7-Flash, and 10.3 points of file-path hits below
Summ.+recent for DeepSeek-V4-Flash, $p=0.03$) and better than the short LLM
summaries by 9--16 F1 points ($p<10^{-3}$). SKC thus makes the agent's current
state readable without degrading what the next step needs.

\Cref{tab:ablation} isolates each component. The \emph{ledger} is what retains
state: removing it costs 10.3 / 6.7 points at 4k / 8k, while its budget would
otherwise buy only 0.3--1.5 points of use and 2.5--7.3 of copy. \emph{Deduplication}
adds 2.0 / 4.7 points of state at little cost elsewhere, consistent with
\cref{prop:dedup}. The \emph{learned utility} buys 8.7 points of copy at 4k over
the heuristic priority, at the price of 4.8 points of state---the same
trade-off that $\lambda$ controls. The \emph{safety constraint} lowers staleness (0.5\%
$\to$ 0.3\% at 4k) at no measurable cost. An imperfect extractor (recall 0.7) costs 5 points of state and
triples staleness, the effect predicted by \cref{prop:stale}. Finally, an
\emph{oracle} utility that knows what the next action uses lifts use and copy to
93--95\% with the same budget, framework and state retention: the remaining gap
to chunk-level BM25 on copy is a matter of utility prediction (AUC 0.818 for
our model vs.\ 0.707 for BM25 relevance, \cref{tab:auc}), not of the compaction
layers.

\textsc{StateTrack} lets us vary one factor at a time and compare with the theory
(\cref{fig:synth-budget,fig:synth-stale,fig:synth-recall}; details in
\cref{app:synthetic}). Pinned, slowly changing and frequently changing keys
behave as \cref{prop:window} predicts: windows keep recently written keys and
lose slow ones; selection keeps salient keys but is stale on 13--30\% of probes;
the ledger keeps 90\% of all keys at 2k tokens and 100\% from 4k. Pinning the task
is itself not supersession-consistent---a user's revision of a pinned
constraint is lost while the original stays pinned---which explains the 6\%
stale rate of windows. As trajectories grow from 50 to 800 steps at 4k, window
accuracy falls from 48\% to 28\% and BM25 staleness rises from 24\% to 43\%,
while the ledger stays at 98--100\% (\cref{prop:sufficiency}). The stale rate of
random selection follows \cref{eq:stale} at the measured keep rate
(\cref{fig:synth-stale}), and so does the stale rate of a ledger fed by an
extractor of recall $r$ (\cref{fig:synth-recall}); a raw recent window hedges
against missed writes (at $r=0.7$, 9\% stale instead of 25\%), whereas a
relevance-based extension does not (16\%), as \cref{cor:safe} implies.

\section{Discussion and Limitations}
\label{sec:limitations}

\paragraph{When to use which variant.} SKC-basic maximizes state retention and
is the better choice when the agent must not lose track of its edits, results
and constraints; SKC trades some of that for the information the next step is
likely to use; and $\lambda$ moves continuously between the two. For agents whose
next action often re-types recent text, a lexical relevance term remains a
strong signal---our utility model already uses it, and the oracle bound shows how
much better utility prediction could still gain.

\paragraph{From sufficiency to success.} The ideal reader measures whether
information is present; the LLM-in-the-loop study shows that three different
readers do use it. We did not run agents end-to-end on compressed contexts:
end-to-end solve rates require containerized SWE-bench environments and many
agent runs per method, and are the most important next step. Our analysis
predicts that compressors with stale or missing state cause agents to repeat
work or act on outdated results.

\paragraph{Probe design.} State keys are derived by the same structural parser
that SKC uses, which favors SKC on state probes; we therefore also report
key-free use and copy probes (on which SKC is not uniformly best), the
LLM-in-the-loop study, exact ground truth on \textsc{StateTrack}, and noisy
extractors. The ordering of methods is unchanged for evidence thresholds
$\theta\in\{0.6,0.8,1.0\}$ (\cref{app:results}). The three v2 utility features
(BM25 against the latest agent turn alone and line overlap with recent turns)
were added after a first evaluation and validated on the development split only;
on the test set they change SKC by less than one point.

\paragraph{Scope.} The trajectories come from software-engineering agents with
typed tools, where most state writes can be extracted structurally. Agents whose
state lives in free text (dialogue, browsing) need learned extractors, whose
recall then governs staleness (\cref{prop:stale}). LLM summaries were evaluated
only in the LLM-in-the-loop study, with one summary written per decision point.

\section{Conclusion}

Agent histories are event logs, and what an agent must keep is the current state
those events define. Viewing compression through this lens separates missing
from stale state, explains when common compressors fail---windows forget by age,
supersession-blind selection retains outdated values at a rate that grows with
overwrites---and suggests compaction at three levels: keys, content and
utility. SKC, a model-free implementation, keeps 7--9 points more state than the
best of seven baselines in-domain and 3--6 points more on unseen scaffolds and
LLMs, is as stale-free as a recency window, and doubles the accuracy with which
LLM readers recover the agent's current state, without hurting next-action
prediction. The open problems are utility prediction, which an oracle shows
could close the remaining gap on copied content, extraction for unstructured
state, and end-to-end validation.
